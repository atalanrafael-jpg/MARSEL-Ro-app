# 04 — Canonical Registry

Цель: не допускать повторного смешивания старых веток, версий и данных.

## Статусы

- `KEEP` — текущий канонический объект, используется.
- `MERGE` — полезная часть должна быть перенесена в один канонический объект после проверки.
- `ARCHIVE` — исторический объект, не используется рабочей системой.
- `REMOVE` — доказанный дубликат/мусор, удаляется только отдельным контролируемым изменением.
- `VERIFY` — нельзя классифицировать без проверки.

## Правило веток

| Источник | Статус в текущей системе |
|---|---|
| `main` | BASELINE |
| `act/marsel-unified-system-2026-08-22` | CANONICAL WORK BRANCH |
| остальные ветки | HISTORY / VERIFY |

Наличие ветки не означает, что её код актуален.

## Правило данных

Никакие реальные записи Ro App не копируются в проектную документацию как «текущие» без свежего read-only подтверждения.

## Правило скриптов

Для каждого назначения должен существовать один канонический рабочий скрипт. Старые `v20.x`, `v21.x`, `v22.x` варианты не считаются актуальными только по номеру версии.

Классификация выполняется по:

1. назначению;
2. фактическим импортам/вызовам;
3. workflow, который его запускает;
4. тестам;
5. актуальному API-контракту;
6. последнему подтверждённому CI.

## Правило workflow

Workflow считается частью текущей системы только если:

- находится в текущей канонической ветке;
- его пути/триггеры соответствуют текущей архитектуре;
- используемые скрипты существуют;
- секреты не зашиты в код;
- результат CI относится к commit текущей ветки.

## Rule: old ≠ current

Исторический commit может объяснить происхождение ошибки, но не может подтвердить текущее состояние.

## Направления MARSEL

| Domain | Код | Состояние |
|---|---|---|
| Ювелирные изделия | `JEWELRY` | CORE |
| Часы | `WATCH` | CORE |
| Очки | `EYEWEAR` | NEW DOMAIN |

## Единая система

Все три направления используют один контур:

`Customer → ServiceOrder → ServiceObject → Diagnosis → Estimate → WorkItem/MaterialItem → QualityCheck → Delivery → Payment/Warranty`.

## API Contract Gate

До реализации или изменения API-интеграции обязательно фиксируются:

- официальный источник;
- URL;
- HTTP method;
- path;
- обязательные параметры;
- схема ответа;
- pagination;
- фактический read-only результат.

Если хотя бы один пункт не подтверждён, статус: `VERIFY`, а не `PASS`.

## Read-only boundary

Эта каноническая ветка не должна выполнять запись в live Ro App во время аудита/верификации.
