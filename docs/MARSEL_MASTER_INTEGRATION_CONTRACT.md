# MARSEL ROAPP — Master Integration Contract

**Status:** v1.0 — contract baseline
**Mode:** READ-first; production WRITE disabled

## 1. Purpose

MARSEL ROAPP is the orchestration/control plane between operational systems and external channels. It must not create a second uncontrolled operational source of truth.

## 2. Canonical entities

Customer, Lead, Product, Order, Repair, Production, Material, Stone, Metal, Warehouse, Payment, Delivery, Marketplace, MarketingAttribution.

## 3. Required identity model

Every synchronized entity SHOULD expose:

- `canonical_id`: stable MARSEL ROAPP identifier
- `source_system`: authoritative upstream system for the record
- `external_id`: identifier in that system
- `lifecycle_status`: explicitly enumerated state
- `created_at`, `updated_at`: source timestamps where available
- `correlation_id`: trace across one business operation
- `audit_id`: immutable audit event identifier
- `reconciliation_status`: `UNKNOWN | MATCHED | DRIFT | BLOCKED`

A field is not considered verified merely because it appears in documentation or code. Live/documented evidence must establish the actual RO App contract before production synchronization is enabled.

## 4. Source-of-truth rules

| Domain | Default owner | MARSEL ROAPP role |
|---|---|---|
| Operational orders | RO App, once live contract is verified | orchestration + reconciliation |
| Warehouse stock | RO App, once live contract is verified | read/audit + synchronization |
| Customers/leads | verified CRM/channel source | identity mapping + orchestration |
| Payments | payment provider | payment state projection |
| Delivery | delivery provider | delivery state projection |
| Marketplace listings/orders | marketplace | adapter + reconciliation |
| Marketing attribution | channel/analytics provider | attribution projection |

No ownership may be inferred from a guessed API field or endpoint.

## 5. Integration invariants

1. Every adapter is isolated behind a provider contract.
2. READ and WRITE capabilities are separately gated.
3. WRITE is disabled by default.
4. Mutating operations require idempotency keys and audit events.
5. Reconciliation is mandatory after synchronization.
6. Retries use bounded exponential backoff and respect provider rate limits.
7. Secrets never appear in logs, evidence, fixtures, or committed documentation.
8. Duplicate resolution is review-first; no heuristic deletion or merge.
9. Production readiness cannot be established by CI alone.

## 6. Correlation contract

A request crossing systems should preserve:

`request_id → correlation_id → integration → endpoint → result → evidence_id`

Telemetry must capture latency, HTTP/result status, retry count, rate-limit state, error class and actor without credentials or sensitive payloads.

## 7. Synchronization contract

For each provider:

`READ → NORMALIZE → VALIDATE → MAP → IDEMPOTENCY CHECK → WRITE (gated) → RECONCILE → AUDIT`

Until the production gate is passed, the final WRITE step is prohibited.

## 8. Evidence contract

Production evidence must be generated by an authorized controlled system. GitHub Actions may validate and index supplied evidence but must never fabricate evidence. Required evidence includes backup, restore, reconciliation, duplicate reference, dry-run, idempotency and rollback results.

## 9. Change control

Contract changes require:

- focused branch
- tests
- review
- documented source/evidence
- no direct production mutation
- updated changelog/open-task state where applicable

## 10. Explicit non-goals

This document does not claim that RO App live schemas, credentials, OAuth/MCP authorization, backup/restore evidence, or production WRITE authorization have been verified. Those remain external gates until real evidence is available.
