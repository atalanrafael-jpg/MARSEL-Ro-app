# MARSEL V21.4 — Системные улучшения и контроль качества

Дата: 2026-08-07
Статус: проектная спецификация; без записи в рабочую базу RO App.

## 1. Принцип классификации

Базовая иерархия:

**Тип позиции → Категория → Группа → Вид → Артикул/ID**

Тип позиции отвечает на вопрос «что это по назначению». Категория и группа описывают предметную область. Вид уточняет разновидность. Артикул/ID однозначно идентифицирует конкретную карточку.

Дополнительные независимые признаки:
- назначение: продажа / производство / ремонт / сервис / комплектующая / внутреннее использование / имущество / клиентское изделие;
- состояние: новое / исправное / неисправное / повреждённое / требует диагностики / в ремонте / готово / выдано / списано / архив;
- происхождение: MARSEL / клиент / поставщик / изготовлено по заказу / металл клиента / собственный материал / стороннее изделие.

Не кодировать назначение и состояние внутри названия карточки.

## 2. Металлы

Рекомендуемая модель:

**Металл → сплав → проба → цвет → форма/состояние → партия → источник → масса**

Разделять:
- собственный металл;
- металл клиента;
- остаток;
- возвратный остаток;
- технологический остаток;
- лом;
- металл, переданный на аффинаж;
- результат аффинажа.

Контролировать отдельно массу изделия, массу металла, массу камней и массу прочих компонентов. Не назначать фактические нормы потерь без подтверждённых технологических данных MARSEL.

## 3. Камни

Карточка камня при наличии соответствующих данных должна поддерживать:
- вид;
- природный/синтетический;
- форма;
- размер;
- масса;
- цвет;
- чистота;
- качество;
- происхождение;
- сертификат;
- номер сертификата;
- поставщик;
- закупочная стоимость;
- фото.

Для бриллиантов предусмотреть отдельные атрибуты 4C: carat, color, clarity, cut.

## 4. Спецификация изделия (BOM)

Для собственного изделия предусмотреть:

**Изделие → компонент → количество/масса → единица → источник → себестоимость**

Компоненты могут включать металл, камни, детали, запчасти и расходные материалы, если они действительно входят в состав изделия.

BOM не должна автоматически создавать физический остаток: спецификация и складская карточка — разные сущности.

Справочник операций:

## 6. Маршрут производства

Шаблон маршрута:

**Заказ → дизайн → 3D → модель → литьё → обработка → пайка/сварка → закрепка → полировка → контроль → упаковка → выдача**

Фактически используемые этапы должны определяться видом изделия и реальным технологическим процессом, а не создаваться автоматически для каждого заказа.

- функции;

- внешний вид;
- фото до работ.

Не создавать обязательность поля, которого нет в реальной конфигурации RO App.

## 9. Риски и предупреждения

Автоматические флаги качества:
- повреждённый камень;
- ослабленная закрепка;
- деформация;
- риск повреждения при ремонте;
- требуется согласование;
- клиент отказался от дополнительной работы;
- материал клиента;
- нестандартная запчасть;
- отсутствующая деталь;
- несоответствие описания и фактического состояния.

## 10. Часовые запчасти и совместимость

Для запчасти при наличии данных:
- производитель;
- артикул;
- reference;
- модель часов;
- калибр механизма;
- совместимые модели;
- размер;
- материал;
- состояние;
- новый/бывший в употреблении;
- поставщик;
- срок поставки.

Нельзя автоматически считать две запчасти совместимыми только по похожему названию.

## 11. Инструменты

Дополнительные поля:
- инвентарный номер;
- серийный номер, если есть;
- ответственный;
- место хранения;

- дата выбытия.

Инструмент не списывать как обычный расходник при каждом заказе.

**покупка → установка → эксплуатация → ТО → ремонт → проверка → выбытие**

Рекомендуемые поля:
- инвентарный номер;
- серийный номер;
- производитель;
- модель;
- дата покупки;
- гарантия;
- поставщик;
- стоимость;
- ответственный;

- документы;
- фото.

## 13. Поставщики

Связи:

**Поставщик → материал / камень / деталь / запчасть / расходник / оборудование**

Дополнительные данные:
- артикул поставщика;

- срок поставки;

- дата последней цены;
- история цен;
- документы.

Рейтинг поставщика не заполнять без фактических данных/критериев.

## 14. Минимальные остатки и закупка

Для складской позиции, если RO App поддерживает поле:

**остаток → минимальный остаток → точка заказа → рекомендация закупки**

Правила должны различаться для металлов, камней, дорогих запчастей и массовых расходников. Нормы не придумывать.

## 15. Партии

Партия может содержать:
- номер партии;
- поставщика;
- дату поступления;
- количество/массу;
- стоимость;
- остаток;
- историю использования.

Особое внимание: металлы, камни, химические материалы, расходники и запчасти.

## 16. Себестоимость

Разделять:

### Материальная
- металл;
- камни;
- детали;
- запчасти;
- расходные материалы.

### Производственная
- работа мастера;
- технологические операции;
- дополнительные производственные расходы, если они реально учитываются.

### Полная
**материальная + производственная + подтверждённые дополнительные расходы**.

Хранить отдельно плановую и фактическую себестоимость, если это поддерживается RO App.

## 20. Data Quality Engine

Уровни:
- OK;
- WARNING;
- REVIEW;
- ERROR.

Проверки:
- орфография;
- пунктуация;
- дубли;
- классификация;
- единицы измерения;
- цены;
- остатки;
- артикулы;
- штрихкоды;
- категории;
- группы;
- связи;
- склад;
- серийные номера;
- обязательные поля.

Технические URL, Markdown и кодовые блоки исключать из лингвистического контроля, чтобы не повторять ранее выявленные false positive.

## 21. Duplicate Engine

Проверять отдельно:
- ID;
- артикул;
- штрихкод;
- точное название;
- нормализованное название;
- производитель + модель;
- reference;
- серийный номер;
- комбинацию ключевых атрибутов.

Результат:
- UNIQUE;
- POSSIBLE_DUPLICATE;
- DUPLICATE;
- REVIEW.

Автоматически объединять карточки нельзя без подтверждённого правила и резервной копии.

## 22. Unit-of-Measure Validator

Проверять соответствие типа позиции единице измерения.

Примеры контроля:
- металл — масса, если такая модель учёта доступна;
- камни — количество и/или масса согласно фактической модели;
- изделия — штуки;
- запчасти — штуки, если учитываются поштучно;
- расходники — реальная единица закупки/расхода;
- инструмент — штуки;
- оборудование — штуки.

Нельзя автоматически менять единицу существующей карточки без проверки движений и остатков.

## 23. API Capability Matrix

Для каждой возможности фиксировать:

**Сущность → endpoint → HTTP method → доступ → read/write → фактический результат → дата проверки**

Минимальный перечень:
- товары;
- материалы;
- категории;
- группы;
- услуги;
- заказы;
- склады;
- остатки;
- клиентские изделия;
- инструменты;
- оборудование;
- поставщики;
- документы.

`YES` ставится только после фактического успешного API-теста. Наличие страницы документации не считается доказательством доступности endpoint для конкретного аккаунта.

## 24. Безопасность API

Все discovery/inventory/mapping этапы должны быть read-only.

Запрещено считать этап успешным, если:
- выполнен POST/PUT/PATCH/DELETE без отдельного разрешённого этапа;
- отсутствует отчёт о фактических запросах;
- невозможно подтвердить `WRITE_REQUESTS=0` для read-only pipeline;
- результат получен из предположения вместо фактического API.

## 25. Dry-run

Перед любым изменением:

**получить → нормализовать → сопоставить → показать diff → проверить дубли → проверить обязательные поля → сформировать план изменений → только после отдельного разрешения выполнить write.**

Dry-run не должен изменять рабочую базу.

## 26. Контроль клиентского имущества

Клиентское изделие должно иметь отдельный признак принадлежности и не смешиваться с собственным складским товаром MARSEL.

Для клиентского изделия желательно хранить связь:

**клиент → заказ → изделие → приёмка → фото → диагностика → работы → материалы → мастер → контроль качества → выдача**.

## 27. Финальный Quality Gate

Перед переходом к write-интеграции требуется:

- API inventory — PASS;
- entity mapping — PASS;
- duplicate check — PASS;
- taxonomy check — PASS;
- units check — PASS;
- required fields — PASS;
- safety audit — PASS;
- dry-run — PASS;
- `WRITE_REQUESTS=0` на read-only этапах;
- `RO_APP_DATA_MUTATED=False` на read-only этапах.

Наличие хотя бы одного критического ERROR блокирует write.

## 28. Правило достоверности

Не создавать автоматически:
- реальные остатки;
- цены;
- себестоимость;
- поставщиков;
- артикулы;
- серийные номера;
- технологические нормы;
- совместимость запчастей;
- фактические характеристики камней;
- оборудование, которого нет в исходных данных.

Если значение не подтверждено — `UNKNOWN` или `REVIEW`, а не догадка.
