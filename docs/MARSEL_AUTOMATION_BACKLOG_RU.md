# MARSEL — карта автоматизации и контроля

## Приоритет P0 — безопасность и соответствие

1. READ-ONLY API inventory.
2. API data contract.
3. Полный аудит пагинации.
4. Резервная копия/экспорт до любой записи.
5. Dry-run изменений.
6. Дубликаты клиентов, товаров, услуг, заказов.
7. Проверка обязательных полей.
8. Проверка ГИИС ДМДК/УИН/именника для применимых операций.
9. Раздельные маршруты производства, продажи, ремонта и клиентских изделий.
10. Журнал всех изменений.

## P1 — производство

- карточка изделия;
- металл: вид, проба, масса, стоимость;
- камни: вид, количество, масса, характеристики, стоимость;
- нормы расхода;
- фактический расход;
- отходы/возврат;
- себестоимость партии;
- себестоимость единицы;
- этапы производства;
- мастер и ответственный;
- контроль качества;
- фото до/после;
- готовность к продаже.

## P1 — ремонт

- прием изделия клиента;
- описание дефектов;
- фото до ремонта;
- масса до ремонта;
- плановая работа;
- материалы;
- масса после ремонта;
- изменение существенных характеристик;
- контроль ГИИС ДМДК;
- контроль клеймения, когда применимо;
- акт выдачи;
- гарантийный период;
- фото после ремонта.

- напоминания клиенту;
- запрос отзыва после выдачи.

## P2 — автоматические события RO App

RO App Public API поддерживает вебхуки для ряда событий, включая клиентов, заказы, задачи, лиды, счета, продажи и бронирования. Это следует использовать для событийной архитектуры, а не для постоянного бессистемного опроса API.

Примеры:

`новый лид → создать задачу → назначить ответственного → срок ответа`

`новый заказ → проверить обязательные поля → сформировать производственные задачи`

`изменение статуса ремонта → уведомить клиента → создать следующий этап`

`закрытие продажи → запрос отзыва → задача на повторную коммуникацию`

`просрочка задачи → эскалация руководителю`

## P2 — электронная торговля

RO App Public API v2 предоставляет методы для каталогов, заказов, счетов и связанных сущностей. Перед подключением интернет-магазина требуется сначала подтвердить текущий API-контракт и модель остатков.

## P2 — контроль прибыли

Цель 3 000 000 руб. чистой прибыли в месяц должна считаться не по выручке, а через модель:

`чистая прибыль = выручка − себестоимость − фонд оплаты труда − налоги − комиссии − реклама − аренда − прочие расходы`.

Автоматически рассчитывать:

- прибыль на заказ;
- маржу по категории;
- маржу по мастеру;
- маржу по каналу продаж;
- стоимость привлечения клиента;
- повторные продажи;
- загрузку мастерской;
- стоимость простоя;
- долю срочных заказов;
- средний срок исполнения.

## P3 — предложения по улучшению

- автоматическая проверка аномально низкой маржи;
- автоматическая проверка отрицательной/нулевой себестоимости;
- предупреждение о снижении складского остатка;
- контроль залежавшихся материалов;
- контроль заказов без следующего действия;
- контроль клиентов без повторного контакта;
- еженедельный отчет владельцу;
- ежемесячный отчет по прибыли;
- автоматический список пяти самых прибыльных и пяти самых убыточных типов работ;
- отдельный отчет по ремонту часов;
- отдельный отчет по ремонту ювелирных изделий;
- отдельный отчет по изготовлению на заказ.

## Что пока нельзя автоматизировать без дополнительного подтверждения

- изменение налогового режима;
- передача юридически значимых сведений в государственные системы;
- массовое удаление или объединение записей;
- изменение идентификаторов изделий;
- автоматическое изменение массы металла;
- автоматическое проведение операций, влияющих на остатки драгоценных металлов;
- автоматическая публикация цен без проверки себестоимости.

## Правило внедрения

`AUDIT → BACKUP → DRY-RUN → APPROVAL → WRITE → VERIFY → REPORT`

Любая операция WRITE должна иметь доказуемую причину, журнал до/после и возможность повторной проверки.
