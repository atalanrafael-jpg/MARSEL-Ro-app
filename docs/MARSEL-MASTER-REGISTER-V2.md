# MARSEL MASTER REGISTER V2

Дата контрольной точки: 2026-08-21

## Назначение
Единый контрольный реестр проекта MARSEL / ROAPP. V2 не заменяет исторический V1; он фиксирует актуальную контрольную модель и не повышает статус без фактических доказательств.

## Статусы
- **CONFIRMED** — подтверждено фактическим результатом, кодом, тестом или доступным артефактом.
- **DESIGNED** — архитектура/спецификация создана, production-внедрение не подтверждено.
- **IN_PROGRESS** — работа выполняется, финальный результат не подтверждён.
- **REVIEW_REQUIRED** — есть изменение или сигнал, но доказательств для CONFIRMED недостаточно.
- **BLOCKED** — безопасное завершение невозможно без внешнего условия.
- **NOT_IN_SCOPE** — исключено из текущего этапа.

## Единая бизнес-модель
1. Изготовление и продажа ювелирных изделий.
2. Ремонт ювелирных изделий.
3. Ремонт часов.
4. Ремонт очков.

## Системный контур
`Клиент → Заказ → Изделие/услуга → Диагностика/производство → Работы и материалы → Склад → Контроль качества → Оплата → Выдача/доставка → Аналитика`

Каждое направление должно использовать общий контур, но иметь собственные услуги, технологические операции, материалы, себестоимость и KPI там, где это необходимо.

## Текущий статус направлений
| Направление | Архитектура | Production факт |
|---|---|---|
| Ювелирное изготовление/продажа | DESIGNED | REVIEW_REQUIRED |
| Ювелирный ремонт | DESIGNED | REVIEW_REQUIRED |
| Ремонт часов | DESIGNED | REVIEW_REQUIRED |
| Ремонт очков | CONFIRMED как проектная спецификация | REVIEW_REQUIRED |

Важно: наличие документа не является доказательством настройки ROAPP.

## P0 — блокеры production-write
1. Подтвердить безопасный полный backup или подтверждённый экспорт.
2. Проверить восстановление backup.
3. Завершить фактическую endpoint matrix.
4. Выполнить полный READ-only аудит clients/products/services/warehouses/documents и связанных сущностей.
5. Сформировать кандидатов исправлений.
6. Выполнить dry-run.
7. Получить отдельное подтверждение на конкретные write-операции.
8. После каждой серии write выполнять reconciliation.

## Ремонт очков — обязательные технические проверки
- существует ли фактическая сущность/категория услуги в ROAPP;
- поддерживает ли схема заказа направление ремонта очков;
- какие статусы реально доступны;
- как связаны клиент, заказ, изделие, услуга и материалы;
- как учитываются детали и списание;
- как рассчитывается себестоимость;
- какие поля можно безопасно использовать для фото/описания дефектов;
- какие права нужны сотрудникам;
- какие API endpoints подтверждены фактически.

До этих проверок статус production остаётся REVIEW_REQUIRED.

## CI / качество
CI считается PASS только при фактическом успешном run без пропущенных обязательных проверок и с доступными доказательствами. Ошибки импорта, тестов, конфигурации и отсутствующие artifacts считаются блокирующими соответствующий gate.

## Безопасность
- READ-ONLY FIRST.
- Секреты не сохраняются в репозитории.
- Не использовать production credentials в тестах.
- Не выполнять массовые POST/PATCH/PUT/DELETE до P0.
- Не считать наличие API-клиента доказательством доступности endpoint.
- Не считать документацию доказательством production-внедрения.

## Definition of Done для каждого бизнес-направления
- модель данных подтверждена;
- справочники подтверждены;
- статусы подтверждены;
- роли подтверждены;
- складской учёт подтверждён;
- себестоимость подтверждена;
- тесты проходят;
- CI проходит;
- artifacts существуют;
- фактическая интеграция ROAPP подтверждена;
- reconciliation выполнен.

## Правило целостности
Если данные, код, тест, документация и фактический API противоречат друг другу, статус устанавливается **REVIEW_REQUIRED**, пока противоречие не разрешено доказательствами.

## Запрет на ложную готовность
Проект не объявляется «100% готовым» до прохождения всех обязательных gates. Непроверенные элементы явно перечисляются как REVIEW_REQUIRED, NOT_RUN или BLOCKED.
