# MARSEL BUSINESS CONTINUITY V1

## Цель

Сохранить управляемость бизнеса при недоступности Ro App, API, интернета, кассы или внешней интеграции.

## Сценарии отказа

### Ro App недоступен

1. Не выполнять массовые изменения.
2. Зафиксировать время отказа.
3. Использовать утверждённый временный журнал операций.
4. После восстановления выполнить reconciliation.
5. Не импортировать повторно уже подтверждённые операции.

### API недоступен

1. Остановить автоматические sync jobs.
2. Сохранить последнюю успешную точку синхронизации.
3. Пометить данные как stale.
4. Повторить запрос после восстановления.
5. Сверить итоговые остатки/заказы.

### Marketplace недоступен

1. Не считать заказ подтверждённым только по локальному событию.
2. Сохранить внешний идентификатор, если он известен.
3. Повторять операции идемпотентно.
4. После восстановления выполнить reconciliation.

### Интернет/сеть недоступна

1. Продолжить только операции, которые можно безопасно фиксировать локально.
2. Не обещать клиенту синхронизированное наличие без проверки.
3. После восстановления синхронизировать по времени операции.

### Касса/платёжный контур недоступен

1. Не имитировать успешную оплату.
2. Зафиксировать заказ как ожидающий оплаты.
3. Возобновить продажу только после восстановления допустимого платёжного сценария.

## Backup policy

Минимальная цепочка:

`Backup → integrity check → test restore → production change → reconciliation`

Backup считается подтверждённым только после проверки возможности восстановления или получения официального подтверждения механизма восстановления.

## API safety

- READ-only является базовым режимом.
- Массовые POST/PATCH/PUT/DELETE запрещены до прохождения P0 из MASTER REGISTER.
- Для импортов используется идемпотентный ключ внешней операции.
- Ошибки не должны молча перезаписывать данные.

## Recovery record

Каждый инцидент должен фиксировать:

- время начала;
- компонент;
- последний успешный sync;
- затронутые операции;
- восстановление;
- reconciliation result;
- ответственного.

## Целостность

После восстановления обязательно проверить:

- количество записей;
- уникальные IDs;
- отсутствие сиротских связей;
- остатки;
- заказы;
- статусы;
- финансовые итоги, если соответствующий источник данных доступен.
